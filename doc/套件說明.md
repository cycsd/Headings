
## MindMapMd 的主要目的

MindMapMd 的核心目的，不是把 Markdown 變成另一套格式，而是提供一個**以 Markdown 原始結構為基礎的視覺化編輯方式**。使用者仍然編輯同一份 Markdown 文件，但可以用更接近 mind map 的方式理解目前的階層、群組關係與段落位置。

具體來說，這個套件主要要解決的是：

- 讓使用者更容易看出 Heading、Paragraph 與子群組之間的從屬關係。
- 讓原本在純文字 Markdown 中不容易觀察的「同層關係」、「群組邊界」與「上下文位置」變得直覺。
- 提供比原生 Markdown 更容易操作的結構調整方式，例如移動區塊、升降階層、合併區塊與 drag and drop。
- 在視覺化操作的同時，仍然回寫成正常可讀、可維護的 Markdown，而不是引入另一套資料格式。
- 幫助使用者在長文或多層級筆記中，降低因結構複雜而造成的編輯成本與理解成本。

換句話說，MindMapMd 比較像是 **Markdown 的結構化視圖與操作層**，而不是取代 Markdown 的編輯器。它的價值在於：保留 Markdown 的可攜性與可讀性，同時補上原生 Markdown 在大型結構編輯上的不足。

## Mind Map MD View Layout

當使用者開啟 Mind Map View 時，套件不會把 Markdown 轉換成另一種儲存格式，而是把原本線性的 Markdown 內容，重新投影成一個更容易閱讀結構的視覺化版面。

在原始 Markdown 中，Heading、Paragraph 與不同層級的內容，都是依照單純的上下文字順序排列。這種形式雖然易於編寫，但當文件變長、層級變多時，使用者不容易快速看出：

- 哪些段落屬於哪個 Heading
- 哪些區塊處於同一層
- 哪些內容是平行群組，哪些內容是某個區塊的子內容
- 如果要移動、合併或調整階層，實際上會影響哪一段結構

Mind Map View 的作用，就是把這種線性的文件，轉成一種接近 mind map 的排列方式，讓使用者可以直接從版面看出「主節點」、「子節點」、「同層節點」與「群組邊界」。

在這個視圖中：

- 文件本身會作為整體的根節點
- Heading 會作為上級節點
- Paragraph,List item, quote..等內容，會作為 Leaf 節點

也就是說，Mind Map View 不是單純把 Markdown「畫成方框」，而是把 Markdown 的文件結構重新表達成可操作、可閱讀的空間關係。這樣做的目的，是讓使用者在保留原本 Markdown 編輯模型的前提下，更直覺地理解與操作複雜結構。

下面這個例子說明的是：同一份 Markdown 文件，如何從原本的線性文字排列，映射成 Mind Map View 中的視覺化布局。

原始 Markdown：
```markdown
yaml
# HeadingA
paragraph_a1
## Heading_A2
paragraph_a2
# HeadingB
#### Heading_B4
paragraph_b1
paragraph_b2
### Heading_B3
paragraph_b3
# HeadingC
paragraph_c1
```

對應的 Mind Map View：
```text
                                         +----------------+
                                         | paragraph_a1   |
                                         +----------------+
                        +------------+   +----------------+   +----------------+
                        | # HeadingA |   | ## Heading_A2  |   | paragraph_a2   |
                        +------------+   +----------------+   +----------------+
+-------------------+   +------------+   +----------------+   +----------------+
| Document Name     |   | # HeadingB |   | #### Heading_B4|   | paragraph_b1   |
| yaml              |   +------------+   +----------------+   +----------------+
+-------------------+   +------------+   +----------------+   +----------------+
                        | # HeadingC |   | ### Heding_B3  |   | paragraph_b2   |
                        +------------+   +----------------+   +----------------+
                                         +----------------+   +----------------+
                                         | paragraph_c1   |   | paragraph_b3   |
                                         +----------------+   +----------------+
```

## 基本邏輯
如果在同一層(同一個 Column)

對於同個群組下面的才適用...
上面的階層肯定比下面的小，因為如果在同一層，如果你的階層又比下面的大，那麼下面的 Block 理應是你的下一層

ex:
可能有這樣的 markdown 結構
```markdown
# Heading1
### Heading3
## Heading2

```
那麼 Heading 3 與 Heading 2 會在同一層，且上面的 Block Heading3 肯定比 下面的 Block Heading2 階層還小

```text
# Heading 1 - ### Heading3
            - ## Heading2
```


如果是這樣的 markdown 結構
```markdown
# Heading1
## Heading2
### Heading3

```
呈現方式要是這樣
```text
# Heading 1 - ## Heading2 - ### Heading3
            
```

而不是這樣
```text
# Heading 1 - ## Heading2
            - ### Heading3
```

但如果是不同群組，則在同一層 還是會有上面的區塊 level 比下面大的情況，
**或許是一種可以用來判定是否是群組邊界的方法？**
Heading B 屬於 Heading A 群組，
paragraph c 屬於 Heading C 群組，
而依照架構 Heading B 與 paragraph c 在同一層(Column)。
```markdown
## Heading A
### Heading B
paragraph a
paragraph b
## Heading C
paragraph c

```
呈現方式會是

```text
## Heading A - ### Heading B   - paragraph a
                               - paragraph b
## Heading C - paragraph c
```
